# Sanity delivery and security contract

Status: production architecture contract for ZebraByte Website.

This document defines how `www.zebrabyte.ro`, `stag.zebrabyte.ro` and the ZebraByte Sanity Studio interact. It complements `sanity-cms.md` and `sanity-full-source-of-truth.md`.

## Core decision

Sanity is the editorial source of truth. It is not the public request-time application backend.

Normal production flow:

```text
Sanity Content Lake
  -> one published snapshot query per website build
  -> validation / normalization
  -> Astro build + existing ZebraByte release gates
  -> Cloudflare Worker + Static Assets
  -> public visitor
```

Normal public requests therefore do not fetch page content from Sanity. Public traffic scales primarily against Cloudflare, while Sanity usage scales with editorial activity, previews and builds.

## Monthly usage model

The architecture optimizes usage without disabling useful Sanity features.

- A normal website build consumes one Content Lake query for all published CMS document families.
- The existing blog migration reuses that snapshot instead of issuing a second Content Lake query.
- Draft edits do not trigger production builds.
- A publish/update/unpublish event may trigger one Cloudflare build through the private deploy hook.
- Public page views do not trigger Content Lake queries.
- Preview/editor traffic may query Sanity as needed; it is intentionally isolated from public traffic.
- Blog hero images are transformed and copied into the website build output rather than making every public visitor consume Sanity asset bandwidth.
- As other page families migrate, their production media should follow the same build-time/cache-first principle where practical. Do not sacrifice editorial image tooling merely to avoid all Sanity asset usage.

Do not hard-code Sanity commercial plan ceilings into application behavior. Limits and plans can change. The operational objective is to keep normal monthly usage comfortably below the current account limits while retaining full editorial capability.

## Published snapshot

`tools/sync-sanity-site.mjs` is the single build-time entrypoint for published ZebraByte CMS content.

It must:

1. use the exact configured ZebraByte project and dataset;
2. use the live `api.sanity.io` endpoint for static builds so a publish is immediately visible to the build;
3. explicitly request the `published` perspective;
4. fetch all supported document families in one GROQ request;
5. validate singleton IDs, routes, slugs and URL schemes before writing the snapshot;
6. write only to the ignored `.sanity-cache/` build cache;
7. never serialize an API token or deploy-hook secret into the snapshot;
8. fail the build on malformed or unsafe published content.

If validation or Sanity retrieval fails, the new deployment must fail closed. The previously deployed production version remains the serving version.

## Route ownership

The CMS owns editorial routes, not runtime namespaces.

The following prefixes are reserved and cannot be created as CMS page/legal routes:

- `/api`
- `/cdn-cgi`
- `/.well-known`
- `/en`

`/en` is generated by the ZebraByte localization architecture from the canonical Romanian route. Editors must not create a second English route manually.

New reserved runtime namespaces must be added to both the Studio policy and the build validator before they are introduced publicly.

## Link policy

CMS-authored destinations may be:

- a canonical internal ZebraByte path;
- a local anchor;
- an `https:` URL;
- `mailto:`;
- `tel:`.

HTTP and script-like schemes are not accepted. Rich-text annotations use the same policy as CTA/navigation links.

External embeds/scripts are not an editorial field. A new external integration requires a code change, security review and CSP review.

## Code versus CMS ownership

Sanity may control:

- text and rich text;
- RO/EN content;
- media references;
- SEO metadata;
- navigation/footer content;
- approved page sections and their ordering;
- approved component variants;
- jobs, guides, stories and legal content;
- editorial publication state.

Sanity must not control:

- arbitrary HTML, CSS or JavaScript;
- Worker routing;
- CSP/security headers;
- WAF rules;
- Cloudflare bindings;
- secrets or API tokens;
- Turnstile validation;
- form destination/verification logic;
- authentication/authorization logic;
- rate limits;
- webhook verification;
- deploy-hook credentials.

## Preview security

Draft content is a privileged editor surface.

The Presentation Tool trusts only:

- `https://stag.zebrabyte.ro`;
- local development origins.

`www.zebrabyte.ro` is deliberately not an allowed draft-preview origin. Production remains published-only.

`SANITY_STUDIO_PREVIEW_URL` is validated by Studio configuration and cannot silently point at an arbitrary third-party origin.

When draft mode is implemented on staging:

- validate Sanity preview URL secrets server-side;
- use a Sanity Viewer/read token only on the server/Worker;
- never expose the token through `SANITY_STUDIO_*`, `PUBLIC_*`, client JavaScript or generated HTML;
- use the `drafts`/requested release perspective only after the preview handshake succeeds;
- disable API CDN use for draft/release perspectives;
- enable Content Source Maps/stega only for authenticated preview requests;
- use `HttpOnly`, `Secure`, `SameSite=None` and `Partitioned` preview cookies where required by the Presentation iframe model;
- protect `cms.zebrabyte.ro` and staging with Cloudflare Access where operationally feasible;
- make staging frame policy allow only the CMS origin needed for Presentation; do not weaken production framing policy to make preview work.

## CORS

CORS entries are account configuration, not a substitute for authorization.

Use exact trusted origins. Do not add `*` or broad ZebraByte wildcards.

The self-hosted Studio origin `https://cms.zebrabyte.ro` requires the Sanity account CORS configuration appropriate for authenticated Studio use. Add staging/browser origins only when an implemented browser interaction actually requires them.

## Publishing webhook

The Sanity webhook targets a private Cloudflare Workers Builds Deploy Hook for the public website.

- Keep the deploy-hook URL secret.
- Do not commit it.
- Do not expose it in Studio browser environment variables.
- Use a narrow published-content webhook filter covering the CMS document families that actually affect the website.
- Draft changes must not trigger production builds.
- Rotate the hook if disclosure is suspected.

## Provenance and claims

Sanity makes editing easier; it must not make unsupported claims easier to publish.

Testimonials and story/case-study records include internal provenance notes. Those fields are editorial evidence and are not rendered publicly. Existing ZebraByte provenance checks remain authoritative. CMS migration must not relabel inherited Probo customers, people, certifications or relationships as ZebraByte facts without independent evidence.

## Migration rule

Migrate the existing site into Sanity route by route. For each route:

1. capture current-main content and component mapping;
2. populate Sanity without changing the visible design;
3. render through approved components;
4. verify Romanian root and `/en` parity;
5. verify SEO, accessibility and interaction behavior;
6. compare against current-main output;
7. only then remove the old hard-coded content source.

`/compliance-portal` and other sensitive/product-specific surfaces remain untouched unless their migration is explicitly scoped and tested.

## Failure behavior

Security-first means a bad editorial change cannot silently become a runtime compromise.

- Invalid CMS route/link/content contract -> build fails.
- Sanity unavailable during a new build -> build fails; previous production stays live.
- Preview authentication fails -> no draft content; fall back/deny rather than exposing a draft token.
- Deploy-hook compromise -> rotate the hook; it grants build triggering, not Sanity read/write access.
- Studio compromise -> Cloudflare Access/Sanity account controls limit access, and CMS still cannot directly modify Worker security logic.

## Required checks

A Sanity/site delivery change is not ready for main until all existing website gates pass plus:

```text
Sanity dependency audit
Sanity Studio build
zebrabyte-cms Wrangler dry-run
published snapshot sync/validation
public website build
zebrabyte-website Wrangler dry-run
```

Operational deployment and Sanity dashboard/CORS/webhook state must be verified separately; a green repository build does not prove those account-level settings exist.
